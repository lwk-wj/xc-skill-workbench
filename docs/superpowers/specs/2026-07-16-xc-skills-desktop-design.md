# XC Skills Desktop 设计规格

日期：2026-07-16<br>
状态：已通过对话确认并完成书面审阅

## 1. 背景

XC 团队已经维护 `xc-skills` CLI，用于管理 Skills、Rules 和 Workflows，并支持中央仓库、本地与远程模式、多个 Agent、项目级与全局安装、复制与软链接、同步、发布和版本历史。

当前缺口是缺少桌面可视化工具。用户无法方便地了解中央仓库、全局环境和多个业务项目中安装了哪些资产、版本是否一致、软链接是否有效，也无法通过安全的图形界面完成按项安装、更新、卸载或临时停用。

XC Skills Desktop 将提供 macOS 优先的 Electron 桌面应用，并让桌面端与现有 CLI 共享同一套无交互业务核心，避免两套实现逐渐偏离。

## 2. 产品目标

V1 必须做到：

1. 统一浏览中央仓库、全局安装和用户登记的多个项目。
2. 以 Skills 为核心，完整支持浏览、安装、更新、卸载、冻结和解冻。
3. 对 Rules 和 Workflows 提供简化的浏览、安装、更新和卸载能力。
4. 展示资产来源、分组、版本、安装位置、安装方式和健康状态。
5. 支持中央仓库分支的临时切换，并允许用户显式设为默认分支。
6. 复用现有 CLI 配置和系统 Git 凭据，不在应用中存储 Token。
7. 所有写操作可预览、需确认、可报告进度，并能在失败时回滚。
8. 交付可安装的 macOS `.dmg` 和 `.zip`；V1 不包含 Apple 签名、公证或自动更新。

## 3. 非目标

V1 不包含：

- 编辑中央仓库中的资产内容。
- 删除中央仓库中的源资产。
- 在桌面端执行 `sync`、`publish`、Git 提交、打标签或版本回滚。
- 应用内 Git 登录、Token 管理或 SSH Key 管理。
- 自动扫描整块磁盘寻找项目。
- Windows 或 Linux 安装包。
- 向业务项目写入安装清单。
- Apple 签名、公证和应用内自动更新。

桌面端可以展示待同步状态和发布相关信息，但 V1 仅提供 CLI 引导，不直接执行这些高风险流程。

## 4. 用户与使用模型

主要用户是已经使用 `xc-skills` 和一个或多个 AI 编码 Agent 的 XC 开发人员。

应用采用“项目库”模型：

- 用户显式添加项目根目录。
- 应用记住项目的名称和规范化路径。
- 删除项目登记只移除桌面端记录，不删除项目中的任何资产。
- 应用同时提供全局安装总览。
- 应用内置 Codex、Claude Code、Trae 和 Antigravity，并允许新增自定义 Agent。

## 5. 资产范围

### 5.1 Skills

Skills 是 V1 的主要对象。标准资产是包含 `SKILL.md` 的目录，并可包含 `EVOLUTION.md`、引用文件、脚本和其他资源。

完整功能包括：

- 渲染预览和 Markdown 源码查看。
- 文件树查看。
- `EVOLUTION.md` 历史查看。
- 中央、全局和项目安装状态对比。
- 复制或软链接安装，具体可用方式取决于来源。
- 更新、卸载、冻结和解冻。
- 内容哈希、版本、链接和本地修改状态计算。

### 5.2 Rules 和 Workflows

Rules 和 Workflows 作为单文件资产处理，V1 支持：

- 浏览渲染内容和源码。
- 按名称、分组和 Agent 筛选。
- 安装、更新和卸载。
- 内容哈希和安装状态计算。

V1 不为 Rules 或 Workflows 提供演进历史和冻结功能。

## 6. 技术方案

采用“共享 Core API + 薄适配层”方案。

### 6.1 现有 `xc-skills` 仓库

现有仓库负责：

- 抽取无交互、无终端依赖的 Core，并通过 `xc-skills/core` 子路径导出。
- 保留 CLI Adapter，继续使用 Clack 提示、彩色输出和退出码。
- 让现有命令调用 Core，而不是在命令文件中直接实现业务逻辑。
- 保持现有命令名称、参数和默认行为兼容。

Core 源码位于现有仓库的 `src/core`，由同一个 `xc-skills` npm 包通过 `exports` 中的 `./core` 子路径发布。CLI 直接使用内部 Core；桌面端在本地联调时使用精确的本地 package 路径，在交付构建中依赖锁定版本的 `xc-skills` 并导入 `xc-skills/core`。这避免引入新的 npm 包或 Registry 配置。Core 不依赖 Clack、Electron 或 React。

实现阶段必须先记录现有仓库的状态和差异，并采用小范围补丁；不得覆盖、还原或夹带用户的未提交修改。2026-07-16 编写实施计划时，该仓库工作区为干净状态。

### 6.2 新桌面仓库

桌面应用位于本工作区，采用：

- Electron 主进程。
- 隔离的 Preload 层和类型化 IPC。
- React + TypeScript Renderer。
- Vite 系列构建工具。
- 语义化 CSS 变量驱动的浅色和深色主题。

桌面端依赖锁定版本或本地联调版本的 `xc-skills/core`，不复制核心业务逻辑。

### 6.3 进程边界

Renderer 只负责渲染和用户交互。它不能直接访问 Node.js、文件系统或 Git。

Preload 只暴露白名单 API，例如：

- `projects.list/add/remove`
- `agents.list/saveCustom`
- `repositories.getConfig/listBranches/selectBranch/refresh`
- `assets.scan/getDetail/getStatuses`
- `operations.plan/execute/cancel`
- `preferences.get/setTheme`

Electron Main 验证 IPC 参数，调用 Core，维护任务生命周期，并把结构化进度与结果推送给 Renderer。

## 7. Core 领域设计

Core 由职责清晰的模块组成。

### 7.1 Asset Scanner

负责：

- 扫描 Skills、Rules 和 Workflows。
- 识别配置的分组目录。
- 解析 `SKILL.md` frontmatter 中的名称和描述。
- 解析文件、目录和软链接，包括断裂软链接。
- 识别正常入口 `SKILL.md` 和冻结入口 `SKILL.md.xc-disabled`。
- 返回结构化资产记录，不输出终端文本。

### 7.2 Status Engine

每个资产在每个安装位置具有一个状态：

- `not_installed`
- `current`
- `update_available`
- `locally_modified`
- `frozen`
- `broken_link`
- `conflict`
- `invalid`
- `unknown`

状态计算顺序如下：

1. 规范化目标路径并判断入口是否存在。
2. 判断入口是否为冻结入口。
3. 解析软链接并检查真实目标。
4. 对 Skills 读取 `EVOLUTION.md` 版本；对所有资产计算规范化内容哈希。
5. 与当前中央分支中的资产比较。
6. 如果已安装内容不等于中央内容，也无法从版本信息证明是旧版本，则标记为 `locally_modified`，不得自动覆盖。

冻结的 Skill 使用 `SKILL.md.xc-disabled` 内容参与版本和哈希比较，因此可以在保持冻结的情况下更新。

### 7.3 Operations

所有写操作分为两个阶段：

1. `planOperation`：只读检查并返回准确的文件操作、冲突、警告和允许的处理策略。
2. `executeOperation`：使用已确认计划执行，发送结构化进度事件并返回结果。

计划中必须包含：

- 操作类型。
- 资产名称、类型和来源分支。
- 目标项目、Agent 和绝对路径。
- 安装方式。
- 将创建、替换、重命名或删除的具体路径。
- 冲突及解决策略。
- 是否允许取消，以及当前安全步骤边界。

支持的操作为：

- `install`
- `update`
- `uninstall`
- `freeze`
- `thaw`

安装和更新先在同级临时路径准备完整内容，再备份现有目标并原子替换。操作成功后清理备份；失败时恢复备份。

卸载只处理用户选中的单个资产路径，不删除整个 `.agents`、`.codex`、`.claude` 或 `.trae` 目录。

### 7.4 Repository Adapter

负责：

- 读取本地或远程中央仓库。
- 通过参数数组执行 Git，不拼接 Shell 命令。
- 复用系统 Git、SSH、Keychain 和 Credential Helper。
- 设置 `GIT_TERMINAL_PROMPT=0`，认证失败时返回结构化提示。
- 列出本地与远程分支。
- 准备非当前分支的应用缓存快照。
- 在失败时保留最近一次成功缓存并标记为 stale。

### 7.5 Config Adapter

CLI 和桌面端继续共享 `~/.xc-skills-config.json` 中的：

- `mode`
- `repoPath`
- `remoteUrl`
- `defaultBranch`
- `defaultGroups`

读取时进行 Schema 校验。写入时保留未知字段，通过临时文件和重命名完成原子替换。

## 8. 数据存储

### 8.1 共享配置

仓库配置继续使用 `~/.xc-skills-config.json`，确保 CLI 与桌面端行为一致。

### 8.2 桌面端私有状态

以下数据保存在 Electron `userData`：

- 已登记项目列表。
- 自定义 Agent 定义。
- 主题偏好。
- 窗口尺寸和最近选择。
- 仓库缓存和缓存元数据。
- 本地结构化日志。

业务项目中不写入 manifest 或桌面端状态文件。

## 9. 主界面设计

应用使用单窗口、三栏“统一资源浏览器”。

### 9.1 左栏：来源导航

包含：

- 中央仓库。
- 全局安装。
- 用户登记的项目。
- 添加项目。
- 设置。

每个来源显示资产数量或异常数量。项目从列表移除时只删除登记信息。

### 9.2 中栏：资产列表

包含：

- Skills、Rules、Workflows 类型页签。
- 名称和描述搜索。
- 分组、状态和 Agent 筛选。
- 名称、版本、分组、安装数量和健康状态。

选择中央仓库时，标题栏额外显示分支选择器。

### 9.3 右栏：详情与动作

Skills 详情包含：

- 渲染预览。
- Markdown 源码。
- 文件树。
- 演进历史。
- 当前来源分支。
- 各项目、Agent 和全局位置的安装状态。
- 安装、更新、卸载、冻结和解冻动作。

Rules 和 Workflows 使用简化详情，不显示演进历史和冻结动作。

## 10. 主题

应用提供：

- 浅色。
- 深色。
- 跟随系统。

默认是跟随系统，并即时响应 macOS 外观变化。整体采用高信息密度的开发者工作台风格。浅色和深色共用语义化颜色令牌，状态色、Markdown、代码块和焦点状态在两种模式下都必须满足清晰可读要求。

## 11. 项目与 Agent 管理

添加项目时：

1. 打开原生目录选择器。
2. 校验目录存在且可读取。
3. 通过 realpath 去重。
4. 扫描内置及自定义 Agent 的资产目录。
5. 将项目登记到桌面端私有状态。

自定义 Agent 至少包含：

- 稳定 ID。
- 显示名称。
- 项目级基础目录名。
- 全局基础目录。
- Skills、Rules 和 Workflows 的相对目录。

内置 Agent 提供默认值，用户可以停用但不能修改其稳定 ID。

## 12. 安装、更新与卸载

### 12.1 安装

安装向导顺序为：

1. 选择中央资产。
2. 选择项目或全局范围。
3. 选择一个或多个 Agent。
4. 选择允许的安装方式。
5. 生成并展示操作计划。
6. 用户确认后执行。
7. 重新扫描受影响位置并展示结果。

当所选分支等于本地中央仓库当前 checkout 分支时允许复制或软链接。远程来源或应用缓存的其他分支只允许复制，防止软链接指向由应用管理和清理的缓存目录。

冲突策略只针对所选资产：保留本地、替换所选资产或取消。V1 不提供清空整个资产根目录的策略。

### 12.2 更新

- 软链接安装在源内容变化后重新计算状态，通常自动变为最新。
- 复制安装通过原子替换更新。
- `locally_modified` 默认禁止更新；用户必须查看影响并显式选择替换。
- 冻结安装更新时把新来源的 `SKILL.md` 写为目标 `SKILL.md.xc-disabled` 后再原子替换，因此更新后仍保持冻结。

### 12.3 卸载

- 支持项目级和全局安装按单项卸载。
- 预览必须展示将删除的精确路径。
- 卸载不影响中央仓库源资产。
- 如果路径超出已验证的 Agent 资产根目录，操作必须拒绝。

## 13. 冻结与解冻

冻结按“项目或全局范围 + Agent + Skill”这一具体安装位置生效，不影响其他位置。

### 13.1 冻结

- 将安装位置中的 `SKILL.md` 原子重命名为 `SKILL.md.xc-disabled`。
- 对软链接安装只重命名目标位置的链接，不修改中央仓库源文件。
- Skill 目录和其他文件保持不变。
- Scanner 将其识别为 `frozen`。

### 13.2 解冻

- 将 `SKILL.md.xc-disabled` 原子恢复为 `SKILL.md`。
- 如果正常入口已存在，则标记为 `conflict` 并拒绝自动处理。

### 13.3 与其他操作的关系

- 冻结 Skill 仍可查看、更新和卸载。
- 安装向导发现冻结同名 Skill 时，提供解冻或更新后解冻，不重复创建目录。
- Core 和新版 CLI 的 pull/update 必须保留冻结状态，不能因为写入新的 `SKILL.md` 而意外启用。

## 14. 分支选择

中央仓库标题栏提供分支选择器。

### 14.1 行为

- 打开时选中 `defaultBranch`。
- 用户可以刷新远程分支并临时选择其他分支。
- 临时选择只写入当前桌面会话，不修改共享配置。
- 用户选择“设为默认分支”并再次确认后，原子更新 `defaultBranch`。
- 详情页和安装计划始终显示来源分支。

### 14.2 本地与缓存策略

- 当所选分支等于本地仓库当前 checkout 时，直接读取真实工作目录，包含未提交修改。
- 当所选分支不是当前 checkout，或仓库模式为 remote 时，从 Electron `userData` 中的分支缓存读取。
- 缓存目录使用仓库和分支的哈希 ID，不直接将分支名作为文件路径。
- 切换分支不得对用户中央仓库执行 checkout、reset、clean 或其他工作树修改。
- 网络失败时展示最近一次成功缓存，并清楚标记缓存时间和 stale 状态。
- 来自缓存分支的资产在 V1 只允许复制安装。

## 15. 错误处理与恢复

- 单个资产扫描失败不阻断整个来源；该资产显示具体错误。
- 无权限、无效 frontmatter、断裂软链接、入口冲突和 Git 失败使用稳定错误码。
- 用户界面展示可执行的简短说明，详细诊断写入本地日志。
- 日志隐藏 Token、密码、用户名及凭据 URL。
- 写操作在安全步骤边界响应取消，不在文件原子替换中途停止。
- 安装、更新、卸载、冻结和解冻失败时恢复备份并重新扫描。
- 无法完成回滚时进入 `needs_attention` 结果，列出残留路径，不宣称操作成功。

## 16. 安全设计

- BrowserWindow 开启 `contextIsolation`，关闭 `nodeIntegration`。
- Preload 只暴露最小白名单 API。
- IPC 输入和 Core 输入均进行运行时 Schema 校验。
- 所有路径先规范化，再验证其位于允许的中央仓库、项目、Agent 或应用缓存根目录内。
- Git 和其他进程通过可执行文件与参数数组调用，不经过 Shell 字符串解释。
- Markdown 禁用原始 HTML，并清理危险链接协议。
- 外部链接只允许通过 Main Process 的受控流程交给系统浏览器。
- Renderer 不接触系统凭据和完整环境变量。
- 只读浏览、搜索、筛选和分支列表操作不得写入项目或中央仓库。

## 17. 测试设计

### 17.1 Core 单元测试

覆盖：

- 三类资产扫描。
- 分组目录。
- 正常和断裂软链接。
- 正常、冻结和冲突入口。
- 版本解析和规范化内容哈希。
- 全部状态转换。
- 配置校验、未知字段保留和原子写入。
- 路径越界拒绝。

### 17.2 Core 集成测试

使用临时目录和临时 Git 仓库覆盖：

- 本地与远程模式。
- 分支列表、临时切换、缓存和 stale 回退。
- 复制与软链接安装。
- 更新、卸载、冻结、解冻。
- 本地修改保护。
- 中途失败和回滚。

### 17.3 CLI 回归测试

覆盖现有命令和关键参数，确保 Core 抽取后保持兼容。特别验证：

- add
- list
- remove
- pull
- config

- sync 和 publish 的现有边界

### 17.4 桌面测试

- IPC 契约和权限测试。
- React 组件测试：搜索、筛选、来源切换、主题、状态显示和操作计划。

- macOS `.dmg` 和 `.zip` 冒烟测试。

## 18. 验收标准

V1 完成时必须满足：

1. 现有 CLI 命令及参数没有非预期行为退化。
2. 桌面端自动读取现有 `~/.xc-skills-config.json`。
3. 用户可以登记多个项目并查看中央、全局和项目资产。
4. 用户可以按具体项目和 Agent 安装、更新、卸载、冻结和解冻 Skill。
5. 卸载单个 Skill 不会删除整个 Agent 目录。
6. Rules 和 Workflows 可以浏览、安装、更新和卸载。
7. 分支切换不会改变用户中央仓库的工作树。
8. 临时分支不会写回配置；显式设为默认后 CLI 与桌面端使用相同默认值。
9. 来自非当前或远程分支的资产显示来源，并使用复制安装。
10. 只读操作不修改项目或中央仓库。
11. 每个写操作都展示准确影响、要求确认、报告进度，并在失败时尝试回滚。
12. 浅色、深色和跟随系统三种主题正常工作。
13. 应用可以构建为可启动的 macOS `.dmg` 和 `.zip`。

## 19. 实施边界与顺序

实施计划应按以下依赖顺序拆分：

1. 在现有 CLI 仓库建立 Core 契约、测试基线和兼容适配。
2. 实现扫描、状态、配置和 Repository Adapter。
3. 实现操作计划、原子执行、回滚和冻结机制。
4. 创建 Electron 安全骨架和类型化 IPC。
5. 实现项目库、统一资源浏览器和详情页。
6. 实现安装、更新、卸载、冻结和解冻交互。
7. 实现分支选择与缓存。
8. 完成主题、错误体验、端到端测试和 macOS 打包。

每一阶段开始前都必须重新检查并保留现有 CLI 仓库中的用户修改；不得假设实施期间工作区会一直保持干净。
